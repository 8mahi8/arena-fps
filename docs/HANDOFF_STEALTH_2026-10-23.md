> **最初に読む文書。** 次の担当AIはこの文書と現在のGitHubコードを読んでから、ユーザーと基本ルールを議論すること。これは**企画引き継ぎ**であり、「ゲームがすでに実装済み」「以下の試作数値が確定済み」という意味ではない。

## 0. 現在地（重要）

- 状態：**基本設計の議論中。新しい3D潜入1vs1ゲームはまだ未実装。**
- 最優先：**アイテムや特殊能力なしでも成立する** 1vs1の基本ルールを固める。いきなり多機能実装を始めない。
- 前回議論でAIが提案した「一撃捕獲」「装置操作10秒」「ハンターが約10%速い」「侵入者のダッシュ3秒」は**ユーザー未承認**。
- 現在ユーザーは制作の続きを**別のAIに引き継ぐ**予定。この文書は、そのAIがチャット履歴に依存せず再開できるためのもの。
- 初めにユーザーへ聞くなら、**一撃捕獲方式を基本にするか**が重要な論点。ただし一問ずつ細かく確認しすぎず、設計案と反証をセットで示す。

## 1. 作品の核・絶対に守りたい方向性【ユーザーの意思】

学校のiPad（Safari）で友達と遊ぶ、**3D / 両者一人称 / 1vs1専用 / 非対称潜入対戦**。

- **シンプルだけど面白い**。少ない基本操作とルールだけで読み合い・上達・再戦したくなる体験を作る。
- ハンター：施設に侵入したプレイヤーを**探し、捕まえる**。
- 侵入者：姿を隠して装置などの目標を進め、**脱出**する。
- **視界制限、死角、曲がり角、遮蔽物、索敵、先読み、心理戦**をゲームの中心に置く。
- 長時間のチェイスや精密な射撃エイムを中心にしない。見つかれば侵入者がかなり不利だが、障害物を使った振り切り・再潜伏の余地は残す。
- 「FPSは操作負担が大きい」経験から方向転換した。**一人称と3Dそのものはユーザーの希望。安易に2Dへ変更しない**。
- 両役割とも退屈な待機、確定負け、無限の逃げ回りが生じない構造にする。
- 学校用は**音なしでも成立**するよう視覚的手がかりを重視。古いiPadの処理能力やSafari/タッチ操作を優先する。
- 友達と遊ぶ**1vs1が最優先**。過剰なプレイ履歴、ランキング、大量の能力、複雑なメタ進行は不要。
- 費用をかけない方向。新しい有料サービス前提の設計にしない。

**補足：ゲートの狙い**
- マップの反対側に配置するのではない。脱出の方角は限定するが、ハンターが両ゲートを一つの視線・短い往復で完全封鎖できない構造を作る。
- 以前に「ゲート1つ」という案も検討したが、**この引き継ぎ時点の最新案は同じ側に2つ**。
- 2ゲートを置くだけで解決したことにしない。ゲート間の移動時間、視線遮断、侵入者の到達経路、ハンターのキャンプ対策を検証する。

## 3. 未決定だが重要な設計問題

### A. 捕獲：一撃か複数回か
- **AIの推奨たたき台：一撃捕獲。ユーザーの承認はまだない。**
- 一撃なら発見への緊張感と潜伏の意味が強い。一方、偶発的な早期決着や理不尽感が出やすい。
- 複数回なら挽回機会があるが、チェイス中心になりやすく、1vs1でのゲームテンポが変わる。
- 詰める項目：捕獲の成立距離と角度、押しボタンか自動か、壁越しの誤判定防止、捕獲モーション中の隙、視線遮断時の扱い、初動の事故対策。

### B. 装置：操作・中断・通知
- **AIの仮案：1台約10秒、操作中断後も進行度保持、数秒後にハンターへその装置の反応を通知。未承認。**
- 目的：侵入者に「逃げる / 続行する / わざと反応を出して誘導する」という選択肢を作る。
- 注意：操作開始即通知はハンター有利に偏る可能性があるが、通知が弱すぎると索敵材料がなくなる。
- 検討：装置の位置は両者に見えるか / 進行度は誰が見えるか / 通知の内容（位置・範囲・点滅など） / 進行度の保存・減衰・ハンター側の妨害 / 2装置完了時の情報公開。

### C. 移動・発見後の逃走
- **AI仮案：ハンター通常速度約10%速い、侵入者だけ約3秒の短いダッシュ。未承認。**
- 目的：平地での長距離チェイスはハンター有利だが、曲がり角・障害物で視線を切れば侵入者が再潜伏できる。
- 検討：ダッシュの回復条件、ハンターの速度、見つかった後の再潜伏ライン、視野角、カメラ操作の負担、遅いiPadでの同期ずれ。

### D. 隠密・索敵
- **初期候補：遮蔽物、しゃがみ、見える行動痕跡。ロッカーは後回し**というAI提案。未承認。
- 音が聞こえない学校環境でも成立する視覚サインが必要。直接的な透視・常時マーキングは隠密の楽しさを壊しうる。
- ロッカー大量設置は総当たり捜索に陥るおそれ。採用するなら出入りや確認の駆け引きを設計する。

### E. マップ
- 装置4か所、同じ側の2ゲートを含む**小〜中規模の施設**。
- 直線で全体を見渡せない構造。複数ルート、曲がり角、部屋と通路、視線を切れる障害物を使う。
- 監視位置が強すぎる「ハンターの定点待ち」、逆に侵入者が一生見つからない「安全地帯」、ゲートキャンプ、装置の進行を止めるだけで勝てる戦術を検証する。
- マップ寸法、走破時間、スポーン地点、装置の距離、ゲート分岐、迷いやすさはまだ未決定。グレーボックスで試す。

### F. タイマー・勝敗・再戦
- 暫定約180秒。タイムアップはハンター勝ち案。
- 無限潜伏が最善手にならないよう「脱出するために危険を冒す」動機を設計する。
- 早期捕獲が続く・侵入者側ばかり勝つ・ハンターが全く手がかりを得られない、などの偏りを想定する。
- 同一メンバーで役割交代しやすい再戦は重要。複雑な戦績保存より試合のテンポを優先。

## 4. 他AIに期待する企画検討の方法

- 新案を**確定仕様として書かず**、「ユーザー決定」「現在の方向性」「AI仮説」「検証結果」に分ける。
- 各ルールについて「なぜ1vs1で面白いか」「一方的な勝ち筋・悪用は？」「iPad操作負荷は？」を必ず考える。
- ゲームのコアが固まるまでアイテム40種候補などの詳細に飛びつかない。アイテムは**1持ち込み + 現地拾得**の方向だけを保持。
- ユーザーは企画議論に積極的で、反論・改善提案を歓迎する。何でも賛成しない。質問攻めにもせず、まとまった対案を出す。
- 「任した」「任せた」は、合意した方針について調査・実装・検証を自律的に進めてよいという意味。ただし学校で使うGoogle Sites版や既存の公開版を無断で上書きしない。

  - WebGLレンダリングとサイズ追従、描画負荷を抑えた簡易形状、壁判定とRaycasterの例。
- 旧FPSは3体のBOT、射撃・弾薬・リロード・ジャンプ・スライド・死亡/リスポーン等を含むが、**新潜入ゲームに不要なら削除・置換する**。性能や動作安定性を実機で証明済みとは扱わない。

## 6. 公開・通信・検証の注意（ユーザーのゲーム制作フロー）

- 学校で友達と遊ぶ正式な「Googleサイト版」とは、**Google Sitesの「コードを埋め込む」にHTML/CSS/JSを直接貼り、部屋番号などで友達と1vs1ができる状態**を指す。
- **GitHub PagesのURLをGoogle Sitesに埋め込む方法と取り違えない。** GitHub Pagesは開発者の試遊には使えても、学校の運用要件の代替ではない。
- 埋め込みHTMLの単体化は別途必要になりうる。現状の複数ファイル版をそのまま貼るだけで動くと思わない。
- 学校iPadのSafari、Google Sites埋め込み制約、タッチ視点/移動の同時操作、WebGL対応、負荷を早い段階で検証。
- オンライン実装を始める前に、無料枠・接続許可・通信方法・ゲーム状態の権威（捕獲/装置/勝敗の二重確定防止）を決める。接続できると**決めつけない**。
- 1端末でのロジックテストと2端末での通信テストを分ける。ゲスト画面停止や遅延が起きても、描画/入力/通信/状態同期を切り分ける。
- 開発ブランチで実験し、動作確認後にmainへ統合する。ユーザーの許可なく学校で使う版を入れ替えない。

## 7. 推奨する次の進め方（作業順・提案）

1. **基本ルールの意思決定** — 捕獲回数、装置の操作/通知、見つかった後の逃走、隠密サイン、制限時間。
2. **勝ち筋の悪用レビュー** — ゲートキャンプ、装置監視の固定戦術、無限潜伏、確定捕獲、故意の時間稼ぎを紙上で検討。
3. **グレーボックス設計** — 装置4・同側2ゲート・分岐通路を図示。各地点の移動時間・視線・遮蔽物で説明。
4. **アイテムなしの単独シミュレーション** — まずオフラインで双方の役割や擬似BOT/リプレイを使い、装置、勝敗、捕獲、操作の成立を確認。
5. **軽量3D試作と自動/手動テスト** — FPS機構の不要部分を整理。iPadで移動・視点・アクションの同時操作ができるか確かめる。
6. **オンライン1vs1** — 通信基盤を検討し、部屋番号で2端末の対戦/両視点同期/勝敗を検証。
7. **Google Sites直接埋め込み試験** — 完全なHTML納品と学校iPad Safariでの実機検証。問題を修正する。
8. **基本ゲームが面白いと確認できたら** 持ち込み/拾得アイテムの候補を比較し、最小数から追加。

推奨チェック観点：両役割の勝率と体感、1試合の時間、最初の発見までの時間、装置操作中の判断回数、ゲート決戦の読み合い、意図せぬ壁抜け捕獲、入力引っ掛かり、片側だけの通信停止。

## 8. 次のAIがユーザーに提示すべき最初の応答

短く引き継ぎを確認し、**まだ新ゲームは実装していないこと**を明言したうえで、まず捕獲・索敵・装置の3要素がどう駆け引きを作るかを複数案で比較する。

特に直近のAI提案は「**一撃捕獲 + 装置反応の遅延通知 + 侵入者の短距離ダッシュ**」。これは**仮説であって決定事項ではない**。ユーザーに利点/欠点を示し、コアが固まったら次の作業へ進める。
